Ordem de Serviço · Fluxo por dentro do código

Aprovação do orçamento pelo cliente

Este guia acompanha uma única requisição HTTP, do momento em que o cliente aprova o orçamento até a resposta 200 OK, mostrando por quais classes ela passa, em que ordem e por quê.

A requisição atravessa as quatro camadas da Clean Architecture: o controller recebe, o caso de uso orquestra, os agregados do domínio aplicam as regras e os adaptadores de infraestrutura gravam no banco e disparam as notificações. Tudo dentro de uma transação: ou a OS entra em execução e o estoque é baixado, ou nada muda.

Duas portas, o mesmo caso de uso. O cliente aprova pela rota pública /api/publico/ordens-servico/{id}/orcamento/resposta, identificando-se pelo CPF/CNPJ. A oficina pode registrar uma aprovação recebida por telefone pela rota /api/admin/ordens-servico/{id}/orcamento/aprovacao, com JWT. As duas chegam ao mesmo ResponderOrcamentoUseCase; só muda como a OS é carregada (com ou sem conferência do documento). Este guia segue a porta do cliente.

As camadas que a requisição atravessa

Cada camada só conhece a camada de dentro. O domínio não sabe que existe HTTP, Spring ou PostgreSQL. Um teste automatizado (ArquiteturaTest, com ArchUnit) quebra o build se alguém violar essa regra.

interfaces.rest

Interface

Recebe o HTTP, valida o formato da entrada e converte o resultado em JSON. Não tem regra de negócio.

application

Aplicação

Anatomia do controller

O controller é a porta de entrada HTTP. Ele é fino de propósito: traduz HTTP para uma chamada de método e o resultado de volta para JSON. Abaixo, a classe inteira, como está no repositório.

classe completasrc/main/java/br/com/oficina/interfaces/rest/AcompanhamentoClienteController.java
@RestController                                       // (1) responde HTTP e serializa o retorno em JSON
@RequestMapping("/api/publico/ordens-servico")        // (2) prefixo de todas as rotas da classe
@Tag(name = "8. Acompanhamento pelo cliente")         // (3) agrupa as rotas no Swagger
public class AcompanhamentoClienteController {

    static final String CABECALHO_DOCUMENTO = "X-Documento-Cliente";

    // (4) dependências: SÓ casos de uso da camada de aplicação, injetados pelo construtor
    private final ConsultarOrdensServicoUseCase consultar;
    private final ResponderOrcamentoUseCase orcamento;

    public AcompanhamentoClienteController(ConsultarOrdensServicoUseCase consultar,
                                           ResponderOrcamentoUseCase orcamento) {
        this.consultar = consultar;
        this.orcamento = orcamento;
    }

    @GetMapping                                       // GET /api/publico/ordens-servico
    public List<OrdemServicoResponse> listar(@RequestHeader(CABECALHO_DOCUMENTO) String documento) {
        return consultar.listarDoCliente(documento).stream().map(OrdemServicoResponse::de).toList();
    }

    @GetMapping("/{id}")                              // GET /api/publico/ordens-servico/{id}
    public OrdemServicoResponse consultar(@PathVariable UUID id,
                                          @RequestHeader(CABECALHO_DOCUMENTO) String documento) {
        return OrdemServicoResponse.de(consultar.consultarPeloCliente(id, documento));
    }

    @PostMapping("/{id}/orcamento/resposta")          // (5) a rota deste guia
    public OrdemServicoResponse responder(
            @PathVariable UUID id,                                     // (6) id da OS, vindo da URL
            @RequestHeader(CABECALHO_DOCUMENTO) String documento,      // (7) CPF/CNPJ, vindo do cabeçalho
            @Valid @RequestBody RespostaOrcamentoRequest request) {    // (8) corpo JSON validado
        return OrdemServicoResponse.de(Boolean.TRUE.equals(request.aprovado())   // (9) decide a ação...
                ? orcamento.aprovarPeloCliente(id, documento)                     // ...e delega ao caso de uso
                : orcamento.rejeitarPeloCliente(id, documento, request.motivo()));
    }                                                                  // (10) converte o resultado em DTO de saída
}

Peça por peça

#ElementoO que faz
1@RestControllerDiz ao Spring que a classe atende HTTP e que o objeto devolvido pelo método vira o corpo JSON da resposta.
2@RequestMappingPrefixo comum das rotas. Como começa com /api/publico, o SecurityConfig deixa a rota aberta (sem JWT).
3@TagSó documentação: agrupa as rotas no Swagger.
4Campos final + construtorInjeção de dependência. O controller recebe casos de uso, nunca repositórios ou entidades JPA. Quem cria esses objetos é o CasosDeUsoConfig.
5@PostMappingMapeia POST …/{id}/orcamento/resposta para o método responder.
6@PathVariable UUID idLê o {id} da URL e converte para UUID. Se não for um UUID válido, responde 400 antes de entrar no método.
7@RequestHeaderLê o CPF/CNPJ do cabeçalho X-Documento-Cliente. Se faltar, responde 400.
8@Valid @RequestBodyConverte o JSON em RespostaOrcamentoRequest e aplica as anotações de validação (@NotNull aprovado, @Size motivo). Se falhar, responde 400 com a lista de campos.
9A única decisãoEscolhe aprovar ou rejeitar a partir do booleano. É decisão de roteamento, não regra de negócio.
10OrdemServicoResponse.de(...)Converte o resultado do caso de uso (objetos do domínio) no JSON de saída. O domínio nunca é exposto diretamente.
O controller faz
  • Ler URL, cabeçalhos e corpo.
  • Validar o formato da entrada (@Valid).
  • Chamar um método de caso de uso.
  • Converter o resultado em DTO de resposta.
O controller não faz
  • Regra de negócio (status, estoque, orçamento).
  • Acesso ao banco ou a repositórios.
  • Abrir transação (isso é da infraestrutura, no passo 3).
  • Tratar exceções: elas sobem até o TratadorErros, que monta o 4xx.

Transação

A transação abre, sem nenhuma anotação no caso de uso

Proxy do Spring → TransactionInterceptor → ResponderOrcamentoUseCase

Em poucas palavras: todo método público de uma classe *UseCase vira uma transação. Isso é configurado na infraestrutura, então a camada de aplicação continua sem depender do Spring (nem de @Transactional).

configuraçãoinfrastructure/config/TransacoesConfig.java
// métodos de consulta: transação somente leitura
for (String prefixo : List.of("buscar*", "listar*", "consultar*", "calcular*")) {
    atributos.addTransactionalMethod(prefixo, leitura);
}
// todo o resto (ex.: aprovarPeloCliente): leitura e escrita, rollback em qualquer exceção
atributos.addTransactionalMethod("*", escrita);

// aplica o interceptor a toda classe do pacote application cujo nome termina em "UseCase"
ClassFilter casosDeUso = classe -> classe.getPackageName().startsWith(PACOTE_APLICACAO)
        && classe.getSimpleName().endsWith("UseCase");
return new DefaultPointcutAdvisor(new ComposablePointcut(casosDeUso), interceptor);

Por que a transação importa aqui?

A aprovação muda várias linhas em várias tabelas: a OS, o histórico de status e o saldo de cada peça. Se a segunda peça não tiver saldo, a baixa da primeira não pode ficar gravada. A transação garante que tudo seja confirmado junto (COMMIT) ou desfeito junto (ROLLBACK).

Pense num carrinho de compras: ou o pagamento passa e todos os itens saem do estoque, ou nada acontece. Não existe "metade da compra".

public OrdemServico obterDoCliente(UUID id, String documento) {
    Documento doc = Documento.de(documento);           // valida CPF/CNPJ (dígitos verificadores) → 400 se inválido
    OrdemServico os = obter(id);                       // ordens.buscarPorId(id) → 404 se não existe
    Cliente cliente = clientes.buscarPorId(os.getClienteId())
            .orElseThrow(() -> new RecursoNaoEncontradoException("Ordem de serviço", id));
    if (!cliente.possuiDocumento(doc)) {               // documento de outra pessoa
        throw new RecursoNaoEncontradoException("Ordem de serviço", id);   // → 404, e não 403
    }
    return os;
}
OrdemServicoRepository e ClienteRepository são interfaces do domínio (portas). Quem as implementa, com JPA, são os adaptadores em infrastructure/persistence/adapter. O caso de uso nem sabe que existe banco.

Em poucas palavras: a OS confere que está AGUARDANDO_APROVACAO, marca o orçamento como APROVADO, muda para EM_EXECUCAO, guarda o horário de início (usado no tempo médio) e registra os eventos.

private OrdemServicoDetalhe aprovar(OrdemServico os) {
    Instant agora = relogio.instant();
    os.aprovarOrcamento(agora);                              // ← passo 5: regra da OS
    os.getPecas().stream()
            .sorted(Comparator.comparing(ItemPeca::getPecaId))
            .forEach(item -> baixarEstoque(item, agora));    // ← passo 6: uma baixa por peça
    return ordensServico.salvar(os);                         // ← passo 7: grava e publica eventos
}
regra no agregadodomain/ordemservico/OrdemServico.java
public void aprovarOrcamento(Instant agora) {
    exigirStatus(StatusOrdemServico.AGUARDANDO_APROVACAO, "aprovar o orçamento");   // senão → 422
    situacaoOrcamento = SituacaoOrcamento.APROVADO;
    orcamentoRespondidoEm = agora;
    registrarEvento(new OrcamentoAprovado(id, clienteId, getOrcamento().valorTotal(), agora));
    alterarStatus(StatusOrdemServico.EM_EXECUCAO, agora);
    inicioExecucao = agora;                                  // base do "tempo médio de execução"
}

private void alterarStatus(StatusOrdemServico destino, Instant agora) {
    if (!status.podeTransicionarPara(destino)) {             // regras de transição
        throw new TransicaoStatusInvalidaException(status, destino);
    }
    StatusOrdemServico anterior = status;
    status = destino;
    historico.add(HistoricoStatus.de(destino, agora));       // trilha de auditoria
    registrarEvento(new StatusOrdemServicoAlterado(id, clienteId, anterior, destino, agora));
}

domain/estoque/Peca.java · infrastructure/persistence/jpa/PecaJpaRepository.java

Em poucas palavras: para cada peça, o sistema trava a linha no banco (ninguém mais mexe nela até o fim da transação), pede à peça para baixar a quantidade e salva. Se faltar saldo em qualquer peça, tudo é desfeito.

no caso de usoapplication/ordemservico/ResponderOrcamentoUseCase.java
private void baixarEstoque(ItemPeca item, Instant agora) {
    Peca peca = pecas.buscarPorIdParaAtualizacao(item.getPecaId())   // trava a linha da peça
            .orElseThrow(() -> new RecursoNaoEncontradoException("Peça", item.getPecaId()));
    peca.baixar(item.getQuantidade(), agora);                         // regra de saldo
    pecas.salvar(peca);
    publicador.publicar(peca.extrairEventos());                       // ex.: EstoqueAbaixoDoMinimo
}
regra no agregadodomain/estoque/Peca.java
public void baixar(int quantidade, Instant momento) {
    Assercoes.positivo(quantidade, "Quantidade de baixa");
    if (!possuiDisponivel(quantidade)) {
        throw new EstoqueInsuficienteException(nome, quantidadeEstoque, quantidade);   // → 422 + ROLLBACK
    }
    quantidadeEstoque -= quantidade;
    if (abaixoDoMinimo()) {
        registrarEvento(new EstoqueAbaixoDoMinimo(id, codigo, nome, quantidadeEstoque, estoqueMinimo, momento));
    }
}

Por que ordenar as peças por id? Se duas aprovações simultâneas travassem as mesmas peças em ordens diferentes (A→B e B→A), uma esperaria a outra para sempre (deadlock). Com a ordem fixa, a segunda simplesmente espera a primeira terminar.

Pontos de atenção

As decisões de projeto que tornam este fluxo seguro. Vale explicar cada uma no vídeo.

Segurança

Documento errado responde 404, não 403

Se a resposta fosse "proibido", quem tentasse um id qualquer descobriria que aquela OS existe. Com 404, uma OS de outra pessoa é indistinguível de uma OS inexistente.

documento ≠ dono da OS → 404 Recurso não encontrado

Implementado em OrdensServico.obterDoCliente.

Transação

Tudo ou nada

Mudança de status, histórico e baixa de todas as peças são uma única unidade de trabalho. Qualquer exceção desfaz tudo.

exceção em qualquer passo → ROLLBACK de tudo

Configurado em TransacoesConfig, sem @Transactional na camada de aplicação.

Concorrência

Trava pessimista nas peças, otimista na OS

Peças são disputadas por várias OS ao mesmo tempo: travamos a linha (FOR UPDATE), sempre na mesma ordem. A OS raramente é disputada: basta detectar o conflito pela versão (@Version).

peça → SELECT … FOR UPDATE (ordenado por id)
OS → @Version → 409 se houver conflito
Eventos

Notificar só depois do commit

Os eventos nascem nos agregados, mas o listener só roda após o COMMIT. Se a transação for desfeita, nenhuma notificação sai.

evento registrado → transação confirmada → notificação

Implementado com @TransactionalEventListener em NotificacoesListener.

Glossário rápido

Os termos que aparecem neste guia, em palavras simples.

Controller
Classe da camada de interface que recebe o HTTP e chama um caso de uso. Não tem regra de negócio.
Caso de uso (UseCase)
Classe da camada de aplicação que executa uma ação completa do sistema, coordenando agregados e repositórios.
Agregado
Grupo de objetos do domínio tratado como uma unidade, com uma raiz que protege as regras. Aqui: OrdemServico e Peca.
Porta
Interface definida no domínio ou na aplicação (ex.: PecaRepository) que diz o que é preciso, sem dizer como.
Adaptador
Implementação de uma porta usando uma tecnologia (ex.: PecaRepositoryAdapter com JPA).
Proxy
Objeto criado pelo Spring que "envolve" o caso de uso para abrir e fechar a transação em volta de cada chamada.
Evento de domínio
Registro de um fato que aconteceu (ex.: OrcamentoAprovado), usado para reações como notificações.
DTO
Objeto só de transporte: o formato do JSON de entrada (RespostaOrcamentoRequest) e de saída (OrdemServicoResponse).
COMMIT / ROLLBACK
Confirmar ou desfazer, de uma vez, tudo o que a transação alterou no banco.
Problem Details (RFC 9457)
Formato padrão das respostas de erro: status, title, detail, instance.
